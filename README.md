## 1. プロジェクト概要

**SSTV Turbo** は、デジタル画像を音響信号（可聴音）へ変換してスピーカーから出力し、スマートフォン等のマイクで録音した音声をWeb経由でアップロードすることで、元の高解像度画像を段階的・協調的に復元する **音響画像伝送＆集合知アグリゲーションシステム** です。

アマチュア無線（SSTV: Slow Scan Television）や衛星通信（CubeSat等）、インターネットが制限されたオフライン・防災環境、電波法制約下での音響データ転送を想定し、**ノイズ・残響・マイク歪み・振幅変動が激しい室内スマホ録音環境でも100%に近い検出率** を達成する耐ノイズ信号処理を備えています。

### コア機能の特徴
1. **デュアル画像伝送エンジン**:
   - **JPEG モード**: DCT係数とリスタートマーカーを活用し、一部ノイズ混じりでも段階的にざらざら感から輪郭・色彩を復元する高耐性モード。
   - **PNG モード**: Deflate可逆圧縮と厳密なCRC検証・ビット多数決による 0/100 完璧復元モード。
2. **クラウドソーシング型協調アグリゲーション**:
   - 1回の録音ですべてのパケットを受信する必要はなく、**10〜30秒程度の短い録音を複数人（または複数回）アップロード** することで、サーバー上でタイル（格子）が埋まり、集合知として1枚の画像が完成。
3. **高速デコード（実時間の4〜5倍速）**:
   - Numba JIT による超並列4-FSK復調により、30秒の録音ファイルであれば **約8秒以内** にデコード・画像生成・Web反映まで完了。


## 3. 音響信号・変調仕様 (4-FSK)

本システムは、振幅（音の大きさ）ではなく周波数の変調によってデジタルデータを伝送する **4-FSK（4値周波数偏移変調）** を採用しています。音量の揺らぎ（フェージング）やスピーカー・マイク間の距離変化に対して本質的な耐性を持ちます。

### 周波数マップ
| 2ビット値 | 送信周波数 | 役割 |
| :---: | :---: | :--- |
| **同期トーン** | **1,000 Hz** | 各パケット先頭の同期信号 (20 ms) |
| **00** | **8,000 Hz** | データシンボル |
| **01** | **6,000 Hz** | データシンボル |
| **10** | **4,000 Hz** | データシンボル |
| **11** | **2,000 Hz** | データシンボル |

### JPEGモード と PNGモード の信号パラメータ比較

| 項目 | JPEG エンジン (`digital_turbo_jpeg`) | PNG エンジン (`digital_turbo_png`) |
| :--- | :--- | :--- |
| **基準タイルサイズ** | 16 × 16 ピクセル (256タイル) | 16 × 16 ピクセル (256タイル) |
| **サンプリングレート** | 44,100 Hz (16bit モノラル PCM) | 44,100 Hz (16bit モノラル PCM) |
| **シンボル長** | **2.0 ms** / symbol | **3.0 ms** / symbol |
| **伝送レート** | **2,000 bps** (1,000 symbol/s) | **1,333.3 bps** (666.7 symbol/s) |
| **同期トーン時間** | 20 ms (1,000 Hz) | 20 ms (1,000 Hz) |
| **パケットヘッダー** | ImageID(16) + TileX(8) + TileY(8) + Len(16) + CRC(16) = 64 bit | 同左 |
| **総データ量 (256タイル)**| **約 186.9 KB** (平均 730 B/タイル) | **約 100.4 KB** (平均 392 B/タイル) |
| **総音声長** | **約 1,513 秒 (約 25.2 分)** | **約 1,231 秒 (約 20.5 分)** |
| **復元特性** | ざらざら感・段階的復元 | 0/100 多数決厳密復元 |

> **💡 なぜシンボル速度が遅いPNGの方が総再生時間が短いのか？**  
> 16×16の極小タイルの場合、JPEGはJFIFヘッダーやハフマンテーブル、耐ノイズ用のリスタートマーカー（`restart_marker_blocks=1`）の固定オーバーヘッドが大きく、PNG（Deflate）に比べてデータ量が **約1.86倍** に肥大化します。このデータ量の差が伝送速度差（1.5倍）を上回るため、JPEGの方が再生時間が長くなります。

## 4. JPEG画像復元アルゴリズム（No.1 〜 No.5 フローチャート詳解）

JPEGアグリゲータ（[`digital_turbo_jpeg/aggregator_turbo.py`](file:///c:/Users/kosei/OneDrive/Desktop/sstv-png-stand/digital_turbo_jpeg/aggregator_turbo.py)）は、受信した各タイル座標 `(x, y)` のパケット群に対して、以下の優先順位（No.1〜No.5）でフォールバック復元を実行します。

```
[受信パケット群 (同一x,y座標)]
         │
         ▼
[No.1 無傷チェック] ──(100%完全なJPEGあり)──► 【確定保存 (次回多数決スキップ)】
         │ (不合格)
   (パケット複数?)
     ├──[No]──► No.4 へスキップ
     └──[Yes]─┐
              ▼
   [No.2 全ビット加重多数決] ──(完全復元成功)──► 【確定保存 (次回多数決スキップ)】
              │ (不合格)
              ▼
   [No.3 RSTマーカー区間分割再構築] ──(完全合体成功)──► 【確定保存 (次回多数決スキップ)】
              │ (不合格)
              ▼
[No.4 最高SNR単体採用 (有効画素率 >= 85%)] ──(該当あり)──► 【クリア単体描画 (次回再挑戦)】
         │ (全タイル85%未満)
         ▼
[No.5 RGBピクセル空間加重平均合成] ──► 【半透明加重合成描画 (次回再挑戦)】
   (※パケットが1つのみの場合は有効画素率不問でその1枚を描画)
```

### ステップ別詳細規定

#### No.1: 受信タイル単体での無傷チェック・即時採用
- 届いたオリジナルのパケットの中に、最初から 100% 完全な無傷JPEGがあるかを `is_perfect_jpeg_tile()` で厳密検査。
- 完全なパケットが1つでもあれば、他と混ぜずに即座に描画確定し、DBへ `stage="NO1"` として確定永続化（これ以降、同座標では多数決を実施せず即時採用して終了）。失敗すれば No.2 へ。

#### No.2: 全ビット加重多数決
- 複数タイルのビット列全体で SNR を加重値とした多数決を行い、ノイズを相殺して完全なJPEGの復元を試みる。
- 完璧に復元できれば `stage="NO2"` で描画確定しDBへ保存（これ以降の同座標では多数決を実施しない）。失敗すれば No.3 へ。

#### No.3: RSTマーカー区間分割による再構築・多数決
- 16×16タイルの場合、RSTマーカーは3個（RST0, RST1, RST2）で、タイルのペイロードは4区間に分割される。
- 各パケットをRSTマーカー単位で区間分割し、区間ごとに多数決や最良データを抽出してスプライシング（合体）。
- 再構築したタイル全体が完璧に復元できれば `stage="NO3"` で描画確定しDBへ保存。失敗すれば No.4 へ。
- **※重要**: No.2 および No.3 は、DBに対象座標のパケットが複数存在するときのみ実行。**パケットが1つしかない場合は、No.2 と No.3 をスキップして No.4 へ進む**。

#### No.4: 最高SNRタイルのクリア単体採用
- 有効画素率（黒落ちしていない面積）が **85%以上** のタイルがあれば、変色ノイズを防ぐため他と混ぜずに電波強度（SNR）が最も良かった1枚をそのまま単体採用して描画終了。
- **※次回再挑戦**: 100%完全復元ではないため（`final_bytes=None`）、次回以降に新しいパケットが届いた際は再び No.1 から再挑戦される。

#### No.5: RGBピクセル空間での加重平均合成
- すべてのタイルが有効画素率85%未満（半分以上真っ黒など）の場合、同座標にある各タイルを画像展開し、生き残っているピクセル（黒落ち除外マスク）同士を画面上で半透明合成（SNR加重平均）して合作。
- **初受信の1パケットのみの場合**: 有効画素率にかかわらず、ここでその1枚を描画して処理を終了。
- **※次回再挑戦**: 100%完全復元ではないため、次回以降に新しいパケットが届いた際は再び No.1 から再挑戦される。

## 5. 耐ノイズ・スマホ録音対策設計

スマホでの実音響録音（PCスピーカー → スマホマイク）において発生する物理的劣化要因に対し、システム全体で多層的な保護策を講じています。

1. **低周波エアコン・机の振動雑音（50Hz〜300Hz）**:
   - `upload_routes.py`（ffmpeg）および `decoder_turbo.py`（SciPy）の **400Hz〜9,500Hz バンドパスフィルター** により完全遮断。
2. **スマホマイクの音量差・距離変動（フェージング）**:
   - 4-FSK（周波数判定）のため音量の大小に不変。
   - アップロード時の動的ゲイン正規化（`dynaudnorm`）とデコーダー内の相対ピーク比率判定により、音が小さくても正確に検出。
3. **部屋の反響（室内リバーブ・エコー）**:
   - ハミング窓（Hamming Window）によるシンボル中央部の重点積分と、軟判定（Soft-decision）＋第2候補スコア保持による最尤誤り訂正。
4. **PCとスマホの水晶振動子クロック誤差（±0.05% ドリフト）**:
   - 20ms 同期トーンによるパケット単位のリシンク（再同期）により、長時間再生でもクロックズレが累積しない設計。
5. **破損パケットの誤混入防止**:
   - 16bit CRC（誤検出確率 1/65,536）でチェックし、破壊されたパケットは自動廃棄。

## 8. セットアップ & 実行手順

### 必要要件
- Python 3.10 以上 (Windows / macOS / Linux)
- `ffmpeg`（音声形式自動変換用、推奨）

### 1. インストール
```bash
git clone <repository-url>
cd sstv-png-stand

# 仮想環境の作成と有効化
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate

# 依存パッケージのインストール
pip install -r requirements.txt
```

### 2. デモ音声の初期セットアップ
基準画像（`data/input/test.jpg`）から JPEG および PNG のデモ音声を自動生成・配置します。
```bash
python setup_demo_audio.py
```

### 3. アプリケーションの起動
```bash
# 開発サーバー起動 (デフォルトポート: 5000)
python -m web_turbo_png.app

# または本番 Gunicorn 起動
gunicorn -w 2 -b 0.0.0.0:5000 "web_turbo_png.app:app"
```

ブラウザで `http://localhost:5000` にアクセスします。
